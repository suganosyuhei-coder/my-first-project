## 4. シミュレーション

- `requestAnimationFrame` を描画に利用し、シミュレーションは固定時間ステップ（例: 1/60秒）を候補とする。描画頻度とゲーム内時間を分離する。
- 船体状態: `position: {x,y}`, `velocity: {x,y}`, `heading`, `angularVelocity`, `hull`, `inventory`, `maxDistance`, `status`。
- 環境はワールド座標に置き、船体ローカル座標でパーツの取り付け位置を保持する。
- 重心 `C = Σ(m_i * r_i) / Σm_i`。推進力の作用点と重心のずれにより2Dのトルクを近似する。**重心が偏るだけで自動旋回させない。**
- 惑星等の外力は安定性を優先して上限を設け、数値発散・極端な瞬間移動を防ぐ。
- 最低前進保証の詳細（速度ベクトルの補正か船首方向の下限か）は未確定。外力による引き戻しを可能にする要件と両立する案を比較してから決定する。
- 航行距離は `Math.hypot(position.x-start.x, position.y-start.y)` の**最大値**を更新する。

## 5. カメラと描画

- 2D Canvasを航行ビューの有力候補とする（多数の動的物体・軌跡）。SVGはロゴや小規模な線画、HTML/CSSは操作UIに使う。選定は試作・性能比較後に確定する。
- カメラ変換は `screen = world - camera + viewportCenter` を基本とし、回転追従を採用する場合は別途座標変換する。
- 船体の描画中心は画面中央付近に保つ。ワールド位置は固定しない。
- 観測判定はワールド距離、表示判定はスクリーン領域で独立に行う。
- クリック判定はスクリーン→ワールド座標変換を用い、観測済み・画面内の両条件を確認する。

## 6. グリッドクラフト・オートタイル

- 船体を2D整数グリッドで管理する。複数セルを占めるパーツは `origin`, `rotation`, `occupiedCells` を持つ。
- 舟形の基本船体、キャノピー、中核部は重要パーツとして独立した耐久力を持つ。
- 配置検証: 在庫／素材、占有セル、船体接続、重複、重要部分との干渉を確認。細則は未確定。
- 見た目の接続は上下左右の4ビットマスク（N=1,E=2,S=4,W=8、0〜15）で決める方式を候補とする。周辺セルの再描画だけで更新可能。
- **見た目の接続マスク**と**機能ネットワーク**は別データにする。
- UI操作は「選択→配置プレビュー→スナップ→確定」を基本案とし、航行は止めない。
- ドラッグ操作中の再描画負荷を抑え、配置確定時のみ質量・重心等を再計算する案を検討する。

## 7. 資源回収

- 資源状態を `available | collecting | collected` 等で管理する。
- 自動回収は近接判定で、クリック回収は観測範囲と画面内表示を**開始時のみ**判定する。
- クリック回収ジョブに `resourceId`, `startedAt`, `duration`, `progress` を保持する。所要時間は開始距離で確定する暫定案。
- 開始後は観測外・画面外でも進捗が継続する。資源描画が破棄されてもジョブは保持する。
- 回収完了時は一度だけ在庫を増やす。自動回収との競合は資源IDで排他制御する。
- 破壊・終了時に未完了ジョブをどう扱うかは未確定。

## 8. ダメージ・終了

- 破損は部位単位で管理する。一般パーツのHP=0で機能を無効化する。
- `canopy.hp <= 0 || core.hp <= 0` で終了。終了は一度だけ発火し、航行・クラフト・回収を停止する。
- 重要部位以外の破壊では最低前進を維持する。危険地帯はまずダメージルールへの接続を検討する。

## 9. 記録保存

- `localStorage` にバージョン付きデータを保存する（キー例 `shutle.records.v1`）。
- 記録項目: runId、日時、maxDistance、endPosition、endReason、destroyedCriticalPart、必要に応じて間引いた軌跡。
- 保存時の検証、読み込み時の型チェック、壊れたデータの安全な初期化を実施する。
- 毎フレーム保存せず、終了時に記録を確定する。必要なら途中保存は別仕様として検討。

## 10. 検証と実装順序（承認後）

## 12. ビジュアルデザインシステム — ハイブリッド方針 v0.6（2026-10-12 承認）

### 12.1 デザインコンセプトと表現の分担

**「科学図解のようなUIの中で、ドット絵の宇宙船が抽象的な宇宙を航行する」**ことを目指す。添付されたメートルの起源・現在を扱う図解画像の視覚言語を参考にするが、画像全体の模写や数値・図版の転用はしない。

- **宇宙空間:** 2D抽象モーショングラフィックス。円、楕円、軌道、波、流線、点線、ベクトル、星などを連続的に描画する。
- **宇宙船とクラフト:** 舟形船体と細長い試験管状キャノピーを備えた、グリッドベースの拡大ドット絵。船体内外に増設したモジュールを判読可能にする。
- **UI・HUD:** 科学図鑑、計測器、技術資料、設計図を思わせるタイポグラフィ、目盛り、罫線、黒ベタのラベル、等幅数字を使用する。
- 全画面をドット絵化しない。船体は離散的、宇宙の力場や軌道は滑らかな線で対比させる。
- 2D表現を維持し、旧3D砂漠・地上探索の画面構成を復活させない。
- 既存ロゴ \`src/assets/shutle_logo.svg\` は**変更せず使用**する。

### 12.2 色・タイポグラフィ（初期提案値、数値は未確定）

| トークン | 候補色 | 用途 |
| --- | --- | --- |
| SPACE | \`#101820\` | 宇宙背景 |
| PANEL | \`#F5F4F0\` | 計測パネル |
| INK | \`#151515\` | 文字・罫線 |
| SIGNAL | \`#79D2DF\` | 観測・収集 |
| CAUTION | \`#EEAA72\` | 重力・警戒 |
| DANGER | \`#D95757\` | 損傷・危険 |

- 配色方針は暗色の宇宙＋明色の計測UI、白黒を基調とした限定的なアクセント色。
- 日本語は可読性の高いゴシック体、数字・英字は等幅系を候補とする。具体的なフォントとライセンスは実装前に確認する。
- 状態の違いは色だけに依存せず、ラベル、数値、形状、パターンを併用する。
- 目盛りや細線は実際の計測情報と対応させる。情報に関係しない装飾は抑制する。

### 12.3 宇宙の描画と動き

- **通常航行:** 細い流線、星、補助線を用いる。船のワールド移動とカメラ変換に連動し、速度によって流線の動きや長さを変化させる。
- **惑星:** 写実的な球体ではなく円、楕円、経緯線風の線、軌道等を組み合わせた幾何学的図解。大きさ・危険度は線幅だけでなく輪郭、数値、動きでも示す。
- **重力場:** 惑星周辺の同心円、曲がるベクトル線、歪む軌道で表現。表示はゲーム内の重力・外力状態に同期させる。
- **重力波・時空嵐:** 波形の乱れ、線の断裂、局所的な振動で表現。過剰な全画面点滅や画面揺れに頼らない。
- **資源・観測:** 発見済み資源は画面上で識別可能な記号を用い、観測範囲とスクリーン内表示の両条件を満たすとクリック回収を開始可能。収集中は対象への点線や進捗を示す。開始後に対象が画面外・観測外へ移動しても処理は継続する。
- 動きの滑らかさと物理計算の固定ステップは分離し、描画の負荷によってゲーム内時間・判定が変わらないよう設計する。

### 12.4 宇宙船・クラフトグリッドの視覚仕様

- 船体は舟形の基本シルエットを維持。試験管状キャノピーは重要部位として判読できること。
- セル単位で船体・パーツ・損傷を表現し、編集時はピクセル形状を読み取れる倍率で表示する。
- パイプや配線などは上下左右の隣接に応じて端部・直線・曲がり・T字・十字をオートタイルで表示する。
- **外見上の隣接と、電力・燃料・構造等の機能接続は別判定**とし、UI上でも誤認させない。
- 配置プレビューには占有セル、スナップ位置、有効／無効、無効理由、質量・重心・推力等への影響を示す。
- 編集中も航行・危険・回収は通常速度で継続する。船の危険情報を編集UIが隠さない。

### 12.5 HUDと情報優先度

| 情報 | 推奨表現 | 表示条件 |
| --- | --- | --- |
| 今回の最大直線距離 | 大きな等幅数字、目盛り | 常時 |
| 現在速度 | 数値、短い速度バー | 常時 |
| キャノピー／中核部の耐久 | 数値、部位別警告 | 常時 |
| 観測範囲 | 船周囲の円、数値 | 必要時／操作時 |
| 重力・外力 | ベクトル矢印、強度 | 影響時 |
| 資源回収 | 点線、進捗率 | 収集中 |
| クラフト性能 | グリッド、重量、重心、推力 | 編集中 |

- 最大到達距離は**開始点からのユークリッド直線距離の履歴最大値**。累積移動距離を表示上の記録に置き換えない。
- 航行ビューとクラフトグリッドは同時に確認できることを基本とし、狭い画面でのレイアウトは別途ワイヤーフレームで検証する。
- 情報量が多い場合、常時表示する重要情報を優先し、補助情報を段階的に展開する。
- 船の重要部位が破壊されたときは、終了原因と破壊部位を明示する。

### 12.6 アニメーションとアクセシビリティ

1. **連続的:** 船の航行、軌道、力場、流線は滑らかに補間。
2. **離散的:** パーツ配置・破損・接続の絵柄変更はセル単位で明瞭に切り替える。
3. **計測的:** HUD数値、ゲージ、回収進捗は実際のシミュレーション状態に同期。

- 動きを抑える設定（\`prefers-reduced-motion\` 等）を検討し、危険を知らせる情報はアニメーションなしでも認識できるようにする。
- 小さなラベルや細い罫線はコントラストと実表示サイズを検証する。キーボード操作とクリック対象の判別性も考慮する。
- 装飾的なエフェクトは船体・資源・危険情報の判読を阻害しない。

## 13. v0.7 ビット・共通エネルギー・疑似立体船体（2026-10-12 承認）

### 13.1 ビットの状態と回収ジョブ

- 各ビットに一意ID、状態 \`orbiting | outbound | collecting | returning\`、ターゲットID、位置・進捗を持たせる設計を推奨。
- ビットの割り当ては資材の \`requiredBits: 1 | 2\` に従う。1基なら空きビット1基を予約、2基なら両方を同一ジョブへ予約。割当ては原子的に行い、二重回収を防ぐ。
- 自動回収は近接資材を対象とし、クリック回収は**開始時のみ**観測範囲内・発見済み・画面内の条件を確認する。飛行中・回収中に対象が画面外になってもジョブを保持。
- \`orbiting → outbound → collecting → returning → orbiting\` を基本遷移とする。資材への到達、収集時間、帰還の具体的な成立条件は要検討。
- 回収所要時間は**開始時距離と資材の回収難度**から算出する。飛行時間と回収作業時間をどう配分するかは未確定。
- **在庫追加は帰還時を推奨**。対象消滅時の処理、船体破壊時のジョブ停止、回収予約とインベントリ反映を別状態にする。
- 描画はビットの実座標・状態に追従する2D流線・粒子。画面外で描画を省略しても回収ジョブは継続し、演出の有無で回収速度が変わらないようにする。

### 13.2 単一エネルギー供給グラフ

- \`energy\` を**単一の共通リソース**として扱う。建造用素材 \`materials\` と混同しない。電力・燃料別のネットワークは作らない。
- 共通配管のセルと装置の接続口をノード／エッジとする**接続グラフ**を候補とする。接続口の向き、破損、配置変更により再計算する。
- 太陽光パネル＝生成、貯蔵庫＝蓄積、推進・観測・エフェクター＝消費。供給経路がない／エネルギーが不足する装置の依存機能を停止する。
- 供給元から消費先までの経路を判定するが、**貯蔵庫経由を必須とするか、生成元から直接供給可能かは未確定**。
- オートタイルの4方向マスクは描画専用で、機能接続は独立したポート／グラフ判定にする。
- 配管が破壊されたら連結成分と供給状態を再計算する。通電中のみ流れる光を表示し、未接続・供給不足をUIで説明する。
- **最低前進保証は共通エネルギーが0でも有効**。通常推進機能の停止とゲームのベース航行は分離する。
- 数値パラメータ（生成量・消費量・容量・流量）、エネルギー消費優先順位、ビットの消費有無は実装前の判断事項。

### 13.3 共有船体データと2D疑似立体描画

- 船体グリッド／各パーツの形状・位置・向き・耐久力を**唯一のデータ源**として、クラフト表示と航行表示を別レンダラーで描く。
- クラフト表示はセルの配置・接続が分かる拡大ドット絵。航行表示はセルを白い立体ブロック風に描き、上面・側面の濃淡、エッジ、面取りで疑似立体感を出す。**3Dモデル・3D物理は導入しない**。
- 舟形の船体シルエットと細長い試験管状キャノピーを維持する。損傷・増設は両画面に反映する。
- 外観イベントの候補：\`impact\`（傷・凹み・欠け）、\`dustContact\`（汚れ・付着）、\`heatContact\`（焦げ・変色）、\`partDestroyed\`（欠損）。
- **経過時間を外観劣化のトリガーにしない**。外観上の付着・変色と耐久力減少を独立データとして扱う。
- 衝突位置に応じたセルへの損傷割当てや描画負荷対策は後続設計で検討する。

### 13.4 将来の多目的ビーム・亜空間（実装対象外）

- 単一エネルギーを消費し、共通配管接続を要求する**モード切替式の多目的ビーム**を拡張候補とする。
- モード案：\`mining\`（採掘・加工）、\`defense\`（敵撃退）、\`spaceInterference\`（亜空間入口・特殊航路）。
- モード別の消費量・対象種別・効果をデータ駆動で追加できる構造を**将来検討**する。現段階でビームや亜空間のコード、UI、仮挙動を追加しない。
- 亜空間移動と「出発点からの最大直線距離」の整合は未確定であり、瞬間移動による記録更新などを独断で導入しない。

### 13.5 旧仕様との整合と未確定事項

- 従来の「近接時の自動回収」は**ビットによる近接自動回収**へ具体化する。従来の「回収完了時に即在庫追加」は、帰還後追加を**推奨案**として保留し、実装前に確定する。
- v0.6までの「燃料・電力・構造等の機能接続を区別する」という例示は、v0.7で**エネルギーを単一化**したことに合わせて解釈する。**構造的な取り付け接続とエネルギー配管接続は引き続き別物**。
- ビット帰還の所要時間、対象消滅時の扱い、配管の直接供給、エネルギー配分、具体的な疑似立体セル形状は未確定。Codexは勝手に確定しない。

## 14. v0.7 確定事項の実装方針（2026-10-12）

要件11.6を優先し、第13章の対応する「未確定」「推奨」の記述を更新する。今回のユーザー指示により、v0.7の実装・コミット・PR・マージ・公開が許可された。

- `src/prototype/game.js` が共通状態、コマンド、固定時間更新を管理する。航行・クラフト・回収・エネルギーは同じゲーム時計で更新する。
- `collection.js` が資源の予約と2基の状態遷移を管理する。帰還済みビットも協力ジョブ完了まで予約し、在庫追加を1回に限定する。クリックコマンドを近接自動回収より先に処理する。
- `energy.js` が装置接続口と共通配管の連結成分を判定する。配管の絵柄は別処理。装置ごとの蓄積量を保持し、切断・再接続で増殖・消失しないようにする。貯蔵庫の取り外しではその貯蔵庫内のエネルギーを失う。
- 船体・装置の接続口は今回、占有セルの外周にある上下左右を有効とする。流量制限なし。生成12、観測消費3、推進消費8、貯蔵容量160（単位E）の初期値は調整用。
- 最低速度12m/sを通常推進と分離し、稼働エンジンで最大36m/sまで増速。ビット速度80m/s、近接回収半径32m、観測装置の範囲140mを初期調整値とする。
- `ship.js` の同じ船体セル・パーツ・耐久・外観から、`PixelShip.jsx` と `BlockShip.jsx` を描画する。左上固定光源を船体の回転に合わせてローカル方向へ変換する。
- `damage.js` が2D接触を船体座標へ変換し、付着・傷・焦げと耐久を別管理する。宇宙塵・熱領域・岩の簡易接触だけを対象とし、重力物理・敵AIは追加しない。
- 重要部分のOR破壊で共通シミュレーションを停止し、未完了回収を中止。再挑戦で所持品・機体・仕事を初期化する。記録の永続保存は別段階。
- 既存ロゴ、旧3D画面、依存パッケージ、`main` ブランチは変更しない。公開は既存のGitHub Pages手順を利用する。
